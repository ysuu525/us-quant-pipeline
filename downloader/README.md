# CRSP 数据下载器

从 WRDS 把 CRSP 的股票数据拉到本地，存成 parquet 文件。

**它拉的不是整个 CRSP。** 只有五张表，而且每日行情那张只取了其中 42 列、只取指定日期之后的。
详见下面「到底拉了哪些数据」。

跑一次 2000 年至今大概 **3 GB 上下、半小时到两小时**，硬盘留 10 GB 足够。
（如果你在别处看到 15 GB、20 GB 这种数字，那是按不压缩、或者按 1925 年起的全历史算的。见下面「体积到底多大」。）

---

## 准备

需要 Python 3.10 或更新的版本，以及一个能连 WRDS 数据库的账号。

```bash
pip install -r requirements.txt
```

装的是三个包：`wrds`（连数据库）、`pandas`、`pyarrow`（写 parquet 文件）。

---

## 跑起来

```bash
python crsp_download.py --username 你的WRDS用户名
```

第一次运行会问 WRDS 密码。输密码时屏幕上不显示任何字符，这是正常的，打完直接回车。
如果它接着用英文问 `Create .pgpass file now [y/n]?`，输 `y`，密码会记在本机，以后就不用再输了。

用户名也可以放环境变量里，省得每次写 `--username`：

```bash
export WRDS_USERNAME=你的WRDS用户名
```

### 正式跑之前，先做这两件事

**一，确认表和列都在**（几秒钟，不下载任何数据）：

```bash
python crsp_download.py --check-only
```

如果这一步就报错，说明是账号权限或者 WRDS 改了表名，早点发现比跑一小时再挂掉好。

**二，先下一年，量一下实际有多大**：

```bash
python crsp_download.py --start 2020-01-01 --cut 2020-12-31 --out ./试一年
du -sh ./试一年
```

拿这个数乘以你要的年数，就是真实体积——比任何估算都准。顺便也能知道一年要跑多久。

### 参数

| 参数 | 作用 | 不写的话 |
| --- | --- | --- |
| `--start` | 数据从哪天开始，写成 `2000-01-01` 这样 | `2000-01-01` |
| `--cut` | 数据到哪天为止（含当天） | 昨天 |
| `--out` | 存到哪个目录 | 当前目录下的 `crsp_ciz_snapshots/` |
| `--username` | WRDS 用户名 | 读环境变量 `WRDS_USERNAME` |
| `--check-only` | 只检查不下载 | 关闭 |
| `--resume` | 接着上次没下完的继续 | 关闭 |

完整例子：

```bash
python crsp_download.py --start 2010-01-01 --cut 2026-08-13 --out ~/data/crsp
```

## 断了怎么办：`--resume`

网断了、电脑睡了、手滑按了 Ctrl-C，直接：

```bash
python crsp_download.py --resume
```

它会自动找到 `--out` 里最近那个没跑完的快照，接着往下下。已经下完的年份直接跳过，屏幕上会显示「跳过，上次已下完」。

要是有好几个没跑完的、想指定某一个：

```bash
python crsp_download.py --resume ./crsp_ciz_snapshots/crsp_ciz_2026-08-13_20260825T041200Z
```

### 它怎么知道哪些下完了

每份数据下完最后一步是写一个 `_query_manifest.json`。有这个文件 = 这份完整；没有 = 上次写到一半就断了，那个目录会被**整个删掉重下**。

为什么不接着半截往下写：数据库返回的行没有固定顺序，续传时接着写会造成重复或遗漏。整份重来最多损失一年的进度，但保证数据是对的。

### 什么时候它会拒绝续传

以下三种情况会直接报错，让你重新下一份完整的，而不是接着下：

- **`--start` 或 `--cut` 和上次不一样** —— 接着下会让一个快照里混进两个日期范围的数据。
- **数据库的表结构变了** —— CRSP 改了列，前后两批数据对不上。
- **CRSP 期间更新过数据** —— 靠对比「截止日前最新交易日」发现。接着下等于把两个不同版本的数据拼在一起。

报错信息里会写清是哪一种、该怎么办。

一次也不会有数据丢失：重跑会新建一个快照目录，上次那个残缺的原封不动留着（确认没用了手动删）。

## 下载完了得到什么

`--out` 目录下会多出一个以日期命名的文件夹（叫「快照」）：

```
crsp_ciz_2026-08-13_20260825T041200Z/
├── raw/
│   ├── daily/                     每日行情，按年分开
│   │   ├── year=2000/
│   │   │   ├── part-00000.parquet
│   │   │   ├── part-00001.parquet
│   │   │   └── _query_manifest.json     ← 有这个 = 这年下完了
│   │   ├── year=2001/
│   │   └── ...
│   ├── security_info_history/     证券属性历史（股票类型、交易所等）
│   ├── distributions/             分红派息
│   ├── delists/                   退市
│   └── daily_market_indexes/      市场指数收益率
└── metadata/
    ├── snapshot_manifest.json     完工记录（有它 = 整个快照是完整的）
    └── table_inventory.json       用了哪些表、哪些列、列的类型
```

看到 `snapshot_manifest.in_progress.json` 而没有 `snapshot_manifest.json`，说明这个快照没跑完。

每份数据拆成多个 `part-xxxxx.parquet`，读的时候直接指目录，不用一个个读：

```python
import pyarrow.dataset as ds
daily = ds.dataset("那个快照文件夹/raw/daily", format="parquet", partitioning="hive")
print(daily.count_rows())
```

要传给别人，把整个快照文件夹压缩了发过去。

## 到底拉了哪些数据

这是「原样搬运」——只按日期过滤，不做清洗、拼接、复权计算。

| 目录 | 来源表 | 拉了什么 |
| --- | --- | --- |
| `daily/` | `crsp.dsf_v2` | **只有 42 列**，不是全表。按 `--start` / `--cut` 过滤，按年分开存 |
| `security_info_history/` | `crsp.stksecurityinfohist` | 全部列，日期窗口内的 |
| `distributions/` | `crsp.stkdistributions` | 全部列，日期窗口内的 |
| `delists/` | `crsp.stkdelists` | 全部列，日期窗口内的 |
| `daily_market_indexes/` | `crsp.wrds_dailyindexret_query` | 全部列，日期窗口内的 |

那 42 列写死在脚本开头的 `DAILY_REQUIRED`（15 个，缺一个就报错）和 `DAILY_OPTIONAL`（27 个，数据库里没有就跳过）里。要加列直接改这两个列表。

CRSP 里其他表（月频、指数成分、债券等等）这个脚本不碰。

### 体积到底多大

拿脚本真实的 42 列和真实的写盘代码，生成 25 万行（正好是一个 part 文件的大小）实测：

```
一个 part 文件（250,000 行）: 18.3 MB  ->  每行 73 字节
（同样数据不压缩:            23.9 MB  ->  每行 96 字节）
```

CRSP 每天大约 5,500–6,500 只证券，一年 252 个交易日，所以每年 140–160 万行：

| 每年行数 | 一年 | 27 年（2000–2026） |
| --- | --- | --- |
| 130 万 | 0.10 GB | 2.6 GB |
| 160 万 | 0.12 GB | 3.2 GB |
| 200 万 | 0.15 GB | 4.0 GB |
| 250 万 | 0.18 GB | 4.9 GB |

事件表和指数表加起来不到 200 MB，可以忽略。

**为什么别处的数字大得多。** 常见的三个假设，而且会相乘：按内存里 float64 算而不算 zstd 压缩（×4）；按 1925 年起的全历史算而不是 2000 年起（×2.5）；按整张表算而不是脚本实际选的 42 列（×2–3）。凑齐就是 20 GB。

上面这张表里，每行 73 字节是量出来的（量的脚本是 `估算体积.py`，不用连 WRDS，`python 估算体积.py` 就能自己复现），
每年多少行还是估的。想彻底确定，用上面「先下一年」那招——三分钟出准数。

## 压缩会不会损失精度

不会。parquet 用的 zstd 是**无损**压缩，和 zip 一个道理：解开来必须和原来逐位一致。
实测把价格、收益率、`1/3` 和 `0.1` 这种二进制里存不干净的数写进去再读出来，最大差异是 `0.0`。
压缩只是把重复的模式记短一点，不动数值。

真正会改变数值表示的是另一件事，和压缩无关：**数据库里的 `numeric` 列被存成 float64**
（脚本里 `arrow_type_for` 的映射）。postgres 的 `numeric` 是任意精度十进制，float64 是 64 位浮点，
理论上这一步是有损的。实际影响：

- float64 有 15–17 位有效数字；
- CRSP 的价格是 4 位小数、收益率 6–8 位小数，差得很远；
- 要到第 16 位有效数字才会出现 1e-17 量级的误差。

而且 SAS、R、Stata、pandas 处理 CRSP 用的都是同一种 double，这是全行业默认，不是这个脚本的取舍。
（真要十进制精确的话，可以把 `arrow_type_for` 里 numeric 那一支改成 `pa.decimal128`，
但下游多数工具反而不好处理，一般没必要。）

整数列（permno、成交量）存 Int64、日期列存 date32，这两类是精确的，不存在这个问题。

## 出问题的时候

**连不上 WRDS。** 按可能性从高到低：密码打错了（注意大小写）；网络不通，试试连学校 VPN；账号没开数据库直连权限，这个得找学校的 WRDS 管理员。

**说找不到某张表。** WRDS 偶尔会改表名。报错信息里有程序试过的表名，`metadata/table_inventory.json` 里是数据库里实际有的全部表名，对一下就知道该换成什么。

**说某张表缺列。** 同上，CRSP 改了字段。缺的列名在报错信息里。

**中途断了。** `python crsp_download.py --resume`，见上面那节。

**报了一大段看不懂的英文。** 整段贴出来，那是原始错误信息，看得出问题在哪。

## 三处刻意的处理

这几处不是随手写的，是为了避免数据被悄悄弄坏。改代码的时候别顺手「优化」掉——出问题不会报错，只会让数据静静地错：

1. CRSP 用 `9999-12-31` 这种远期日期表示「还没结束」。这类日期超出 pandas 能表示的范围，交给它解析会变成空值。所以 `secinfoenddt` / `securityenddt` 不解析，原样存。
2. 证券属性表里结束日期为空的记录表示「至今有效」，是必须保留的，WHERE 条件里特意放行了。
3. 每份数据的列类型照着数据库里的类型定死，不让 pyarrow 自己猜。否则某一块碰巧全是空值，类型就会漂，几十个 parquet 文件对不上。
